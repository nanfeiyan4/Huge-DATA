# 选题 3｜智能索引推荐与设计 —— 实施方案

> 目标：一份"方法清楚、指标齐全、结论站得住"的课程报告。核心是**用起来便宜、验证得实**：搜索阶段用 PostgreSQL 的 what‑if 代价（HypoPG）秒级评估，最终方案再真实建索引、真实跑查询。

## 0. 一句话定位

在**存储预算约束**下，为给定查询负载挑选一组索引，最大化负载整体收益；
贡献点 = 冗余消除的候选池 + 交互感知的贪心（带增量重估）+ 预算约束 + LLM 候选补充，
并用"代价代理 vs 真实执行"的相关性分析证明推荐结果可信。

- 主战场负载：**JOB（IMDB，113 条复杂 join）**——索引组合收益差异大，最能体现方法价值。
- 对照/维护开销负载：**TPC-H SF1–10**（索引对写入的影响、构建时间）。
- 研究方向（题面推荐内容）：**① 负载感知与候选索引生成**、**② 索引组合与存储预算优化**、**④ 大模型辅助索引设计**。

## 1. 系统与工具

| 项 | 选择 | 说明 |
|---|---|---|
| DBMS | PostgreSQL 16（次选 17） | 题面允许；HypoPG 生态最成熟 |
| what‑if 工具 | HypoPG | 不建索引即评估规划代价，是搜索效率的关键 |
| 数据 | JOB/IMDB（约 GB 级）+ TPC‑H | JOB 查询集公开；TPC‑H 用 dbgen 或 DuckDB `tpch` 扩展生成 |
| 脚本 | Python（psycopg + pandas） | 采集、汇总、出图 |
| 报告图 | matplotlib | 5–6 张核心图 |

**环境三条路（按优先级）**
1. Linux（WSL2 Ubuntu 或实验室服务器）：`postgresql-16` + `postgresql-16-hypopg` 一条 apt 命令，最省事，推荐。
2. Windows 原生：EDB 提供的 PostgreSQL **binaries zip**（免管理员，解压即用）；但 HypoPG 是 C 扩展，Windows 上要 MSVC/msys2 编译，风险高。
3. 装不上 HypoPG 的替代方案：**抽样库代价筛选**——在 10% 抽样库上把所有候选索引真建一次，用 `EXPLAIN` 的 cost（不执行）做搜索；再在完整库上验证 top‑k。多做一步，但完全不依赖扩展，还能顺带分析"抽样代价排名是否可迁移"。

## 2. 方法（四步流水线）

### 2.1 负载解析与特征提取
从 113 条 SQL 中抽取：涉及的表、WHERE 等值/范围谓词列、JOIN 列、ORDER BY / GROUP BY 列、
以及**每列在谓词中的出现频次**（频率 × 选择性 = 收益线索）。

### 2.2 候选生成（方向 ①）
- **规则池**：等值列在前、范围列在后组合成 (c1, c2, …)；JOIN 列单列索引；ORDER BY/GROUP BY 作为尾列追加。去重后约几百个候选。
- **LLM 池（方向 ④）**：把 schema（表、列、类型、行数）+ workload 摘要喂给模型，要求输出 JSON `[{table, columns[], reason}]`；
  做格式校验 + 重试；统计**新增率、冗余率、被最终选中条数**——这就是 ④ 的实验结论，而不是"用了大模型所以更好"。
- 两池合并去重后进入优化。

### 2.3 冗余消除与代价评估
- 前缀覆盖：(a,b) 可覆盖 (a)（同 btree、无其他语义约束）→ 删 (a)。
- 同列集不同顺序：按等值列选择性排序，只留一个。
- 每条候选在 HypoPG 下评估：
  `SELECT * FROM hypopg_create_index($$CREATE INDEX ON t(a,b)$$)` → `EXPLAIN` 取总 cost → `hypopg_drop_index`。

### 2.4 预算约束下的组合优化（方向 ②）
- 目标：`min Σ_q cost(q, S)`，约束 `Σ_{i∈S} size(i) ≤ B`（size 由列宽 + 行数估算）。
- 算法：**贪心前向选择 + 增量重估**：每轮取 `Δ收益 / Δ存储` 最大者，加入后**重算其余候选的边际收益**（消除收益重叠）；
  收尾做 k‑swap 局部精修。
- 对照与消融（4 组）：
  1. 无新增索引（基线的基线）
  2. 全候选贪心、**不做**冗余消除（消融 A）
  3. 贪心、**不做**增量重估（消融 B）
  4. 随机搜索（同预算，同评估次数）
  5. 本方法
- 预算档位：B ∈ {2%, 5%, 10%} × 基表大小（IMDB 约 3.5GB → 约 70MB / 175MB / 350MB）。

## 3. 实验设计与指标

**统一测量协议（第一周就固定，之后不再改）**
`shared_buffers=4GB`, `work_mem=256MB`, `jit=off`, `max_parallel_workers_per_gather=0`（先关并行降噪，中期单开一组验证并行下的结论）；
`random_page_cost=4.0`, `effective_cache_size` 固定；测量前 `ANALYZE` + `CHECKPOINT`；关闭 autovacuum；
每配置 3 次预热 + 5 次取**中位数**；单查询超时 300s 并记录超时数。

| RQ | 问题 | 指标 |
|---|---|---|
| RQ1 | 相对无索引/基线能赚多少 | 负载总时间、几何平均加速比、P95 单查询加速、超时数 |
| RQ2 | 预算怎么影响收益 | 预算–收益曲线、收益/存储帕累托前沿 |
| RQ3 | 代价代理可信吗 | HypoPG planner cost 改善 vs 真实加速的 **Spearman 相关**、排序一致率 |
| RQ4 | LLM 候选有用吗 | LLM 独有候选命中率、被选中条数、冗余率、token 与耗时 |
| RQ5 | 维护代价多大 | 索引存储总量、构建总耗时、TPC‑H 上写负载吞吐下降比例 |

必做项：**结果正确性校验**（每查询改前/改后结果 md5 或校验和一致）、**推荐耗时**（评估次数、总耗时）、LLM 的 **token 用量与推理时间**（题面明确要求）。

**风险与对策**

| 风险 | 对策 |
|---|---|
| HypoPG Windows 编译失败 | 走 Linux / 或 2.1 的抽样库代价筛选替代 |
| JOB 无索引时单查询极慢 | 搜索阶段只用 planner cost；搜索用 30 条代表查询，终评用全 113 条 |
| 物理机噪声、结论被质疑 | 固定参数 + 5 次中位数 + 报告方差；并行开关单独做一组 |
| 均值被少数重型查询主导 | 同时报几何平均与 per‑query 分布图 |
| LLM 输出不规范 | JSON schema 校验 + 重试 + 记录失败率 |
| 收益不明显 | 同时给"存储–收益帕累托"，把"花多少存储换多少收益"作为结论主线 |
